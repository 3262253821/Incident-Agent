# Incident Agent 项目补充优化清单

最后更新：2026-09-14

本文基于 `E:\IncidentAgent` 当前真实代码、自动化测试和既有设计文档整理。目标是先修复会造成越权、敏感数据泄露或结果不可信的缺口，再补可靠性、可观测性和工程化能力。未完成项保持未勾选；只有修改代码并通过回归测试后才勾选。

## 一、当前基线

- [x] **审计基线：完成代码、文档、测试和启动脚本检查**
  - 检查范围：`app/`、`web/src/`、`migrations/`、`tests/`、启动脚本、README 和 MVP 设计文档。
  - 当前测试：`py -m pytest tests -q` → **18 passed，6 个弃用警告**。
  - 当前静态检查：`ruff check app migrations tests` 未通过，主要是迁移脚本和测试文件的导入排序、未使用导入及测试导入路径问题；这不影响当前功能测试，但应纳入 P1 整理。
  - 说明：测试通过代表已覆盖路径正常，不代表权限、敏感数据、真实服务适配和生产可靠性已经完整。

## 二、P0：必须优先修复的安全与正确性问题

- [ ] **P0-1 在分析入口强制校验知识库权限**
  - 涉及文件：`app/incident_agent/routers/incidents.py`、`app/incident_agent/services/incident.py`、`app/incident_agent/services/rag_client.py`。
  - 当前风险：接口只校验 `knowledge_base_id > 0`，随后立即创建并持久化运行记录。如果模型只调用日志分析或服务状态工具而没有调用 `search_knowledge`，Agent 不会向 DevAtlas 验证该知识库是否存在及是否属于当前用户，却仍可能完成分析并保存一个未授权的知识库 ID。
  - 目标流程：鉴权 → 通过 DevAtlas 的知识库详情/授权接口校验 `knowledge_base_id` → 校验通过后才创建 `AgentRun` 并执行 Graph；校验失败直接返回 403/404，不创建运行记录。
  - 完成标准：未授权、已删除或不存在的知识库不能启动分析；日志分析-only 路径也不能绕过权限；增加 API 和服务层回归测试。

- [ ] **P0-2 对故障输入和工具观察做敏感信息脱敏后再持久化**
  - 涉及文件：`app/incident_agent/services/incident.py`、`app/incident_agent/services/storage.py`、`app/incident_agent/graph/nodes.py`、`app/incident_agent/models/agent_run.py`。
  - 当前风险：`AgentRun.input_content` 保存完整日志，`observations` 保存完整工具结果，消息内容还会进入报告提示词；日志中的 Token、密码、数据库连接串、手机号或业务隐私可能被写入 MySQL 和历史接口响应。MVP 设计文档明确要求不能把完整敏感日志写入运行记录，但当前代码尚未实现脱敏。
  - 目标流程：进入 Agent 前识别常见密钥/凭据模式并掩码；持久化只保存脱敏文本或摘要；原始日志不进入 `AgentStep.arguments_summary/result_summary`；必要时增加保留期限和删除策略。
  - 完成标准：使用包含 `Authorization`、`password`、`api_key`、连接串的测试日志，数据库和 `/runs` 响应中均不出现原值；脱敏误报和长度上限有测试。

- [ ] **P0-3 服务端核验报告证据，禁止模型凭空生成来源**
  - 涉及文件：`app/incident_agent/graph/nodes.py`、`app/incident_agent/schemas/incident.py`。
  - 当前风险：`IncidentReport` 只做字段和枚举校验，`evidence` 的 `document_id/version_id/chunk_index` 是否真实存在、是否来自本次工具观察没有服务端校验。模型即使输出格式合法，也可能虚构文件名、版本或引用，前端会把它展示成可信证据。
  - 目标流程：从 `observations` 建立真实证据白名单；报告节点只允许引用白名单中的知识库来源，日志和服务状态来源由服务端补齐；无法匹配时降级或标记为未经验证。
  - 完成标准：伪造来源会被拒绝/降级；真实 DevAtlas metadata 可正常保留；测试覆盖空来源、跨知识库来源和不存在 chunk。

- [ ] **P0-4 给模型调用设置超时、有限重试和失败可观测性**
  - 涉及文件：`app/incident_agent/services/llm.py`、`app/incident_agent/services/incident.py`、`app/incident_agent/graph/nodes.py`。
  - 当前风险：`ChatOpenAI` 未显式设置请求超时或重试策略；网络卡顿可能长期占用请求线程。`execute_incident` 捕获所有异常并只返回统一的“Agent 执行失败”，既无法区分超时/限流/鉴权，也没有记录安全的错误码和阶段。
  - 目标流程：配置连接和读取超时、最多一次有限重试；将模型异常归一化为 `MODEL_TIMEOUT`、`MODEL_RATE_LIMITED`、`MODEL_UNAVAILABLE` 等错误码，并写入步骤状态，不暴露密钥或堆栈。
  - 完成标准：模拟超时、429、5xx 和非法响应时，接口在可控时间内返回降级结果，运行记录保留阶段和错误码。

## 三、P1：稳定性、可观测性和接口质量

- [ ] **P1-1 报告 JSON 增加容错解析或一次修复重试**
  - 当前 `parse_report()` 对 Markdown 代码围栏、前后解释文字或轻微 JSON 格式问题直接失败，导致整次分析降级。
  - 目标：优先提取合法 JSON；仍失败时进行一次受限的结构化修复请求；修复失败才降级。不得无限重试或放宽字段枚举约束。

- [ ] **P1-2 限制上下文大小并按证据边界截断**
  - 当前报告提示词把全部消息和 observations 序列化后发送，RAG 返回内容可能随 `top_k` 增长而膨胀，没有 token 预算。
  - 目标：按 chunk/观察项边界截断，保留来源 metadata；超过预算时在报告中明确“证据已截断”。

- [ ] **P1-3 补齐步骤参数摘要、结果摘要和耗时**
  - `AgentStep` 已有 `arguments_summary`、`result_summary`、`duration_ms` 字段，但当前节点主要只写 tool 名称、状态和错误码，字段长期为空，轨迹无法用于定位慢调用或重放。
  - 目标：保存脱敏后的参数摘要、结果摘要、阶段耗时和模型请求序号；禁止保存 Token、完整日志和完整模型响应。

- [ ] **P1-4 完善运行历史接口的分页、过滤和响应裁剪**
  - 当前 `/api/v1/runs` 最多返回 100 条完整 `RunResponse`，每条可能包含大量 observations、steps 和报告；没有游标分页、状态筛选或摘要接口。
  - 目标：列表接口只返回摘要，详情接口返回完整记录；支持 cursor/limit、状态和时间范围过滤，并为历史数据设置保留策略。

- [ ] **P1-5 增加运行记录并发与事务边界测试**
  - `append_steps()` 通过 `count + 1` 计算索引；同一 run 若被重复追加可能产生唯一约束冲突。`create_run`、`append_steps`、`finish_run` 分成多次提交，异常中断时可能留下 running 状态记录。
  - 目标：明确单次执行的写入锁/幂等策略；异常时补偿为可识别的 failed/degraded；增加重复提交、数据库异常和进程中断测试。

- [ ] **P1-6 补齐鉴权代理和 API 输入错误映射**
  - `DevAtlasAuthClient.login()` 把除 401/403 外的错误统一映射成 502，DevAtlas 的 422 参数错误、429 限流和 5xx 无法区分。
  - 目标：保留安全的上游错误类别和请求 ID；对客户端输入错误返回 422，对上游不可用返回 503/502，对限流返回 429。

- [ ] **P1-7 统一状态常量和错误码，避免字符串散落**
  - `running`、`completed`、`degraded`、`tool_failed`、`report_validation_failed`、`max_iterations` 等状态直接写在多个模块，前后端也各自维护字符串。
  - 目标：后端集中定义状态/错误码，schema 使用 Literal 或枚举；前端维护状态展示映射并覆盖未知状态。

- [ ] **P1-8 增加关键安全和业务回归测试**
  - 当前测试覆盖 Graph 正常/失败、工具适配和基础 API，但缺少：知识库越权、过期 Token、报告伪造引用、敏感日志脱敏、LLM 超时、数据库写入失败、历史 owner 隔离以及限流/大输入。
  - 完成标准：每个 P0/P1 设计都有至少一个可重复的自动化测试；真实模型只做人工联调，不作为唯一测试依据。

- [ ] **P1-9 修复 Ruff 质量门禁并纳入 CI**
  - 当前 `ruff check app migrations tests` 有 29 个导入排序、未使用导入、测试导入路径和 lambda 风格问题。
  - 目标：整理迁移脚本和测试导入，移除未使用 `Path`，将测试路径配置放到统一 pytest 配置；CI 在 push/PR 时执行 ruff、pytest、compileall、Alembic check 和前端 build。

## 四、P2：产品完整性与工程化增强

- [ ] **P2-1 用真实服务状态适配器替换硬编码 mock**
  - 当前 `get_service_status` 只返回 `order-service`、`user-service` 两个固定值，不能代表真实监控系统；必须在产品文档和 UI 中明确这是演示数据。
  - 目标：定义 `ServiceStatusGateway` 协议，先提供 Mock 实现，再接入可配置的监控/注册中心 HTTP 适配器，并保留超时、鉴权和降级。

- [ ] **P2-2 增加工具调用去重、预算和并行策略**
  - 当前模型可在多轮中重复调用同一工具，只有总迭代上限，没有按工具/费用/时间预算；多个独立工具调用也未显式并行。
  - 目标：按 `tool_name + normalized_args` 去重，设置总调用次数、耗时和 token 预算；可并行的只读工具采用受控并发。

- [ ] **P2-3 增加人工评测和证据一致性指标**
  - 当前只有结构和流程测试，没有记录检索命中率、引用准确性、报告通过率、降级率、模型耗时和人工评分。
  - 目标：建立固定故障样例集，分别评估工具选择、证据覆盖、引用正确性和建议可执行性；指标只写真实测量结果。

- [ ] **P2-4 改进 PDF/日志等输入解析与脱敏规则**
  - 当前 Agent 直接接收文本，日志格式、时间范围、服务名和 trace id 没有结构化；上游 DevAtlas 的 PDF 也可能存在 OCR/布局问题。
  - 目标：增加输入预处理、日志级别/时间/服务字段提取、分页或超长分段，并记录解析质量。

- [ ] **P2-5 完善前端会话与失败体验**
  - 当前历史抽屉一次加载全部记录，路由只依据 localStorage 是否存在 Token，登录状态恢复和 401 处理较弱；分析过程不是 SSE，用户只能等待最终响应。
  - 目标：增加分页历史、详情加载、统一 401/403 退出逻辑、取消请求和 SSE/进度事件；不把 Token 写入普通日志。

- [ ] **P2-6 时间、依赖和部署可复现性治理**
  - 当前使用 `datetime.utcnow()`，Python 3.13 会产生弃用警告；requirements 只有下限版本；启动脚本写死 `E:\` 路径和 Windows PowerShell，缺少 CI/容器化方案。
  - 目标：改用带时区 UTC 时间、锁定可验证的依赖版本、通过环境变量配置路径，并增加 CI 与可选 Docker 部署。

## 五、暂不建议直接加入

- [ ] Redis 缓存
- [ ] MCP、多 Agent 或自动修复
- [ ] Kafka、Kubernetes、复杂微服务拆分
- [ ] Reranker、LLM-as-judge（在没有评测集之前）

原因：这些技术不是当前真实缺口。应先完成 P0 权限/脱敏/证据可信度，再用测试证明 P1 问题确实存在，避免为了简历堆叠技术。

## 七、当前结论

Incident Agent 的 MVP 主链路已经能够运行：登录 → 提交故障 → Agent 选择工具 → DevAtlas 检索/日志分析/服务状态 → LangGraph 迭代 → 结构化报告 → MySQL 历史。当前最需要做的不是再加模型或框架，而是先把知识库授权、敏感数据边界和报告引用可信度补齐；完成 P0 后再进入 P1 工程化。
