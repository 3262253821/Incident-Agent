# Incident Agent 项目补充优化清单

最后更新：2026-09-14

本文合并了 DeepSeek 审查版与 Codex 审计版，作为 Incident Agent 唯一的后续优化清单。审查以 `E:\IncidentAgent` 当前真实代码、测试、启动脚本和 `docs/agent-mvp设计.md` 为依据。

## 一、使用规则

### 1.1 打勾的三个必要条件（缺一不可）

一条优化项只有**同时**满足下面三条，才允许把 `[ ]` 改成 `[x]`：

```text
① 代码已实现
② 相关测试通过（并在记录里写下可复现的命令与真实结果）
③ 已提交并推送到 origin/main
```

补充约束：

- **本地验证通过 ≠ 完成**。凡是依赖外部环境才能成立的功能（例如 GitHub Actions 必须真的在 GitHub 上跑起来），只在本地验证过的一律保持 `[ ]`，并在记录里写清"已完成的部分"与"待办"。
- 仅写进文档、只讨论方案、只手工点过一次，都不算完成。
- 记录里必须能回答：改了哪些文件、怎么验证的、**反证是什么**（把修复回退后测试确实会失败）。
- 如果某条被勾选后发现有缺口，必须**退回 `[ ]`** 并记录缺口，而不是补一句"已完成"。

### 1.2 其它规则

- 优先修复安全、权限、数据可信度和会导致请求失控的缺口，再做可观测性、工程化和产品增强。
- 不为了简历堆叠 Redis、MCP、多 Agent、Docker、Reranker 等技术；必须先有真实需求和测试证据。
- `stages/` 是学习练习，不作为正式模块导入；`resume/` 是个人材料；`tmp/` 是本地临时数据。
- 优化过程中保留现有用户注释，不覆盖与任务无关的本地修改。

### 2.3 运行时探针发现

| 探针 | 实际现象 | 判断 |
|---|---|---|
| 请求设置 `top_k=8` | `search_knowledge` 默认仍向 gateway 传 5 | 请求参数未贯通，是真实功能 bug |
| 请求 KB 为 3，模型工具参数传 999 | gateway 收到 999 | 模型可偏离本次请求的知识库范围；DevAtlas 仍会做最终权限校验，因此准确表述是“范围漂移风险”，不是直接绕过上游授权 |
| 首轮模型不调用工具 | 只要报告 JSON 合法就可能返回 `completed` | 零证据被包装成完成，存在幻觉风险 |
| 5 条 run 各 3 个 step | 访问 `.steps` 额外产生 5 条查询 | 历史列表存在 N+1 |
| `error code 15020` | 当前没有误判为 502 | 现有边界碰巧有效，但信号没有命中片段和行号 |

### P0-3 结果可信度和失败语义

- [x] **P0-3-1 零工具证据不能伪装成 `completed`**
  - 涉及：`core/statuses.py`（新增）、`graph/nodes.py`、前端 `constants/status.ts`（新增）、`views/IncidentWorkspaceView.vue`、`components/ReportPanel.vue`、`components/DegradedPanel.vue`、`styles.css`、`docs/agent-mvp设计.md`。
  - 现状：模型首轮不调用工具也可直接进入 report；只要模型伪造一条合法 evidence，就可能显示 `COMPLETED` 和高置信度。
  - 目标：无成功工具观察时返回 `insufficient_evidence` 或强制 `confidence=low`，前端明确展示“未取得工具证据”；不允许仅凭模型自由文本生成可信来源。
  - 完成标准：零工具调用测试返回独立状态；前端不显示绿色完成徽章。
  - 方案选择：采用**独立状态** `insufficient_evidence`，而不是"保持 `completed` 只把 `confidence` 降为 low"。理由是后者用户看到的仍是绿色完成徽章，问题等于没解决；前者状态名本身就说明了原因，也更适合在面试中解释。
  - 完成记录：报告节点通过 Pydantic 校验后新增证据支撑检查：`成功工具观察数 = observations 中 result.ok == True 的数量`；为 0 时强制把 `confidence` 改为 `low`（**只降不升**，模型要求 `high` 也不放行）、`status` 置为 `insufficient_evidence`、追加 `action=check_evidence_support / error_code=NO_TOOL_EVIDENCE` 的 step。只有 `ok=True` 的观察算证据：全部工具失败的报告与完全没有工具的报告同等不可信；混合场景（有成功也有失败）仍算 `completed`。
  - 提交：`2029157`（已在 `origin/main`，用 `git merge-base --is-ancestor 2029157 origin/main` 可核）
  - 顺带收敛状态常量（DeepSeek 审查版 P1-7 的落地）：新增 `core/statuses.py`（`RunStatus` / `InternalRunStatus` / `StepStatus` / `StepErrorCode`），`graph/nodes.py`、`services/incident.py`、`services/storage.py` 中的状态字面量全部改为常量引用；前端新增 `web/src/constants/status.ts`（`RUN_STATUS` / `STATUS_LABEL` / `STATUS_TONE` / `statusLabel` / `statusTone`），未知状态**显示原文并当作警告**，不再默认落入绿色完成分支。同时给 `ReportPanel` 增加 `status` prop 用于展示 `NO TOOL EVIDENCE` 徽章与提示条，`DegradedPanel` 的说明文字改为可传入（证据不足 vs 报告未通过校验）。

  - 对 Pydantic 的 `PydanticSerializationUnexpectedValue`（嵌套 `list[UnverifiedEvidenceItem]` 触发，用 5 种 `model_validate` 入参组合都无法最小复现）采用**精确匹配**的 `filterwarnings` 抑制，并在 `pyproject.toml` 注明理由——不做全局忽略，避免掩盖自己的真实问题。
  - 新增或更新的测试：`tests/test_utc_timestamps.py`（6 条：`utc_now` 为 naive UTC 且跟随时钟、模型默认值与 `finish_run` 在 `DeprecationWarning` 升级为错误时不报错、落库时间确为 naive UTC、超龄回收的 cutoff 与列值同为 naive 不混用、API 序列化为带 `+00:00` 的 ISO 8601）。
  - 是否影响数据库迁移：**否**（已用 `alembic check` 确认无漂移）。是否影响 API 契约：否（序列化格式不变）。
  - 简历可用事实：可以表述为"排查并清除 Python 3.13 的 `datetime.utcnow()` 弃用告警：用实测确认 MySQL DATETIME 与 SQLite 都不保留时区偏移，因此选择 naive-UTC 存储 + API 边界补时区标记的方案，避免了一次对实际存储无影响的列类型迁移"。

- [x] **P1-2-4 统一异常处理器**
  - 当前 `execute_incident` 之外的数据库或 schema 异常仍可能由 FastAPI 返回通用 500；上游错误类别也被过度折叠。
