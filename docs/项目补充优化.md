# Incident Agent 项目补充优化清单

最后更新：2026-09-14

本文合并了 DeepSeek 审查版与 Codex 审计版，作为 Incident Agent 唯一的后续优化清单。审查以 `E:\IncidentAgent` 当前真实代码、测试、启动脚本和 `docs/agent-mvp设计.md` 为依据。

## 一、使用规则

- 只有“代码已修改 + 有可复现验证命令和结果”才能把 `[ ]` 改为 `[x]`。
- 仅写进文档、讨论过方案或手工测试过，不代表已完成。
- 优先修复安全、权限、数据可信度和会导致请求失控的缺口，再做可观测性、工程化和产品增强。
- 不为了简历堆叠 Redis、MCP、多 Agent、Docker、Reranker 等技术；必须先有真实需求和测试证据。
- `stages/` 是学习练习，不作为正式模块导入；`resume/` 是个人材料；`tmp/` 是本地临时数据。
- 优化过程中保留现有用户注释，不覆盖与任务无关的本地修改。

### 2.3 运行时探针发现

| 探针 | 实际现象 | 判断 |
|---|---|---|
| 请求设置 `top_k=8` | `search_knowledge` 默认仍向 gateway 传 5 | 请求参数未贯通，是真实功能 bug |
| 请求 KB 为 3，模型工具参数传 999 | gateway 收到 999 | 模型可偏离本次请求的知识库范围；DevAtlas 仍会做最终权限校验，因此准确表述是“范围漂移风险”，不是直接绕过上游授权 |
| 首轮模型不调用工具 | 只要报告 JSON 合法就可能返回 `completed` | 零证据被包装成完成，存在幻觉风险 |
| 5 条 run 各 3 个 step | 访问 `.steps` 额外产生 5 条查询 | 历史列表存在 N+1 |
| `error code 15020` | 当前没有误判为 502 | 现有边界碰巧有效，但信号没有命中片段和行号 |

- [x] **P0-1-1 修复 `top_k` 全链路未生效**
  - 涉及：`services/incident.py`、`services/tools.py`、`graph/state.py`、`core/config.py`。

  - 目标：请求校验后由服务端固定本次运行的 `top_k`，通过闭包注入工具；模型无论省略、篡改还是传越界值，最终都使用服务端确定值。
  - 完成标准：请求 `top_k=8` 时 gateway 必须收到 8；增加省略、篡改和边界测试；每个配置字段均有真实读取点。
  - 完成记录：`execute_incident()` 解析有效 top_k 后注入 Graph 工具；服务层测试验证 gateway 收到请求值。

- [x] **P0-1-2 禁止模型改变本次知识库范围**
  - 涉及：`services/tools.py`、`services/incident.py`。
  - 现状：`knowledge_base_id` 暴露给模型，模型可把请求 KB 3 改成 999。DevAtlas 最终仍会根据 JWT 做权限校验，所以主要风险是同一用户多个知识库之间的范围漂移、回答与用户选择不一致。
  - 目标：工具只接收 `query`，`knowledge_base_id` 和 `top_k` 由服务端在构造工具时注入；多余参数拒绝或忽略，不能被采用。
  - 完成标准：模型传其他 KB 时不会真正查询该 KB；引用来源始终属于请求的 KB。
  - 完成记录：`search_knowledge` schema 仅暴露 `query`，KB ID 与 top_k 由服务端闭包固定；新增工具 schema 和服务层测试。

- [x] **P0-1-3 清理失效配置与死字段，统一配置来源**

### P0-2 权限和敏感数据边界

- [x] **P0-2-1 分析开始前强制校验知识库归属**
  - 涉及：`schemas/knowledge_base.py`（新增）、`services/authorizer.py`（新增）、`services/incident.py`、`routers/incidents.py`、`docs/agent-mvp设计.md`。
  - 现状：接口只校验 ID 为正整数，`create_run()` 已提交后才进入 Graph；如果模型只调用日志工具或服务状态工具，就不会调用 DevAtlas 检索，未授权/不存在的 ID 也可能落库并完成分析。
  - 目标流程：Bearer 鉴权 → 使用同一 Token 调 DevAtlas 知识库详情/授权接口 → 403/404 立即返回且不创建 run → 校验通过后再执行 Graph。
  - 完成标准：日志-only 路径也不能绕过授权；未授权、不存在和已删除 KB 不产生 `agent_runs` 记录；增加 API 与服务层测试。
  - 完成记录：新增 `KnowledgeBaseAuthorizer` 协议、`HttpKnowledgeBaseAuthorizer`（`GET /api/v1/knowledge-bases/{id}`）与离线用的 `StaticKnowledgeBaseAuthorizer`；`execute_incident()` 在校验失败时抛出 `KnowledgeBaseAccessError`，清理由 router 统一处理；预校验位于 `create_run()` **之前**，因此失败路径不会产生任何 `agent_runs` / `agent_steps` 行。
  - DevAtlas 契约核对：非本人或不存在统一返回 `404`（`backend/app/services/knowledge_base.py` 按 `id + owner_id` 过滤，路由有意不区分 403/404），因此 Agent 也统一返回 `404`，不泄露资源是否存在；`401/403` 映射为 `401`，超时与网络错误映射为 `503`，其他上游错误映射为 `502`。
  - 新增或更新的测试：`tests/test_knowledge_base_authorizer.py`（11 条：HTTP 状态码映射、DevAtlas 真实响应体字段契约、服务层顺序与“不产生 run”）、`tests/test_incident_authorization_api.py`（4 条：API 层 404/401/503 且 `agent_runs` 计数为 0、未知字段先 422 且不触发预校验）；同步修正 `tests/test_api.py` 与 `tests/test_incident_service.py` 中的既有用例以注入离线授权器。
  - 反证：临时把预校验替换为 `pass` 后，上述 6 条测试立即失败（`DID NOT RAISE KnowledgeBaseAccessError` 等），证明测试能真实捕捉该回归。
  - 测试命令与结果：`py -m pytest tests -q` → **36 passed, 18 warnings**；`py -m ruff check app` → 通过；`py -m compileall -q app migrations tests` → 通过。

- [x] **P0-2-2 输入日志和工具观察脱敏后再保存**
  - 涉及：`core/redaction.py`（新增）、`services/incident.py`、`graph/nodes.py`、`graph/workflow.py`、`docs/agent-mvp设计.md`。
  - 现状：`input_content` 保存原始日志；`observations` 保存完整工具结果（包括 RAG 内容）；步骤摘要字段可原样写入；历史接口又会把这些内容返回。
  - 目标：在进入模型和落库前识别并掩码 Bearer/JWT、password、api_key、secret、token、连接串、手机号/身份证等；持久化只保留脱敏文本、长度和来源摘要；原始日志只在本次请求内存中使用。
  - 完成标准：含凭据的测试日志在 MySQL 和 `/runs` 响应中都搜不到原值；正常日志不被误删；输入和观察有明确长度上限。
  - 完成记录：新增纯函数模块 `core/redaction.py`（`redact_text` / `redact_for_model` / `redact_payload`）。脱敏在四个边界生效：① `execute_incident()` 在 `create_run()` **之前**统一脱敏并截断 title/content，脱敏文本成为 State、模型上下文、MySQL 和响应的唯一版本；② `tools` 节点执行后立即对 `ToolMessage.content` 脱敏再交回模型；③ `observe` 节点写 `observations` 前对工具结果递归脱敏；④ `report` 节点校验通过后对 `summary/evidence/possible_causes/troubleshooting_steps/references` 再脱敏一次。长度上限：title 200、content/工具结果 20000 字符，超限追加 `[已截断，原文共 N 字符]`。

  - 是否影响数据库迁移：否（复用现有 `input_content` / `observations` 字段，无新增列）。
  - 是否影响 API 契约：否（响应结构不变，仅文本内容变为脱敏后的版本）。
  - 与 P1-1-2 的关系：`AgentStep.arguments_summary` / `result_summary` 目前仍未被任何节点写入（长期为 `null`），因此本次没有需要脱敏的内容；这两个字段的填充与脱敏合并到 P1-1-2 一起做，避免现在写一套、那时再改一套。

### P0-3 结果可信度和失败语义

- [ ] **P0-3-1 零工具证据不能伪装成 `completed`**
  - 涉及：`graph/nodes.py`、`schemas/incident.py`、`services/incident.py`、前端状态展示。
  - 现状：模型首轮不调用工具也可直接进入 report；只要模型伪造一条合法 evidence，就可能显示 `COMPLETED` 和高置信度。
  - 目标：无成功工具观察时返回 `insufficient_evidence` 或强制 `confidence=low`，前端明确展示“未取得工具证据”；不允许仅凭模型自由文本生成可信来源。
  - 完成标准：零工具调用测试返回独立状态；前端不显示绿色完成徽章。

- [ ] **P0-3-2 服务端核验报告 evidence 来源**
  - 涉及：`graph/nodes.py`、`schemas/incident.py`。
  - 现状：Pydantic 只校验字段、枚举和非空列表；`document_id/version_id/chunk_index/filename/detail` 是否来自本次 observations 没有交叉验证。
  - 目标：从真实 observations 建立证据白名单；knowledge base 来源必须匹配真实 document/version/chunk；日志和服务状态来源由服务端补齐；匹配失败则剔除、降级或标记为未经验证，并记录 `UNVERIFIED_EVIDENCE`。
  - 完成标准：模型编造 `document_id=999` 会被拒绝或降级；真实来源字段完整保留；跨知识库来源不能通过。

- [ ] **P0-3-3 失败时保留确定性的人工可用摘要**
  - 涉及：`graph/nodes.py`、`services/incident.py`、`schemas/incident.py`、前端 `DegradedPanel.vue`。
  - 现状：工具失败、报告校验失败、达到迭代上限时 `report=None`，前端只能看到工具名、状态和错误摘要，已有证据没有结构化结论。
  - 目标：失败后生成不依赖模型的 `degraded_summary`，包含已命中的日志信号、真实来源清单、失败工具/错误码和人工核对建议；不能把模型猜测写成结论。
  - 完成标准：三种失败路径均返回可读摘要，摘要引用只来自真实 observations。

### P0-4 超时、异常和中断

- [ ] **P0-4-1 设置模型超时、有限重试和安全错误码**
  - 涉及：`services/llm.py`、`services/incident.py`、`core/config.py`、`.env.example`。
  - 现状：DevAtlas HTTP 有超时，但 `ChatOpenAI` 没有显式 `timeout/max_retries`；`graph.invoke()` 没有请求总时限；所有异常被折叠成一句通用错误。
  - 目标：配置连接/读取/模型/请求总超时，默认有限或关闭自动重试；归一化 `MODEL_TIMEOUT`、`MODEL_RATE_LIMITED`、`MODEL_UNAVAILABLE` 等错误码，保留安全阶段信息。
  - 完成标准：sleep 假模型、429、5xx 和非法响应都能在可控时间内降级，已有 steps/observations 被保存且不泄露密钥。

- [ ] **P0-4-2 回收被中断的 `running` 记录**
  - 涉及：`services/storage.py`、`routers/runs.py`、`stores/incident.ts`。
  - 现状：进程被杀、OOM 或 reload 后，先 commit 的 `running` 记录可能永久冻结；前端把大多数非 completed 状态混显示为 DEGRADED。
  - 目标：启动时或查询时把超龄 run 标记为 `interrupted`；前端区分运行中、已中断、降级和循环超限，并允许安全重跑。
  - 完成标准：杀进程重启后没有永久冻结的假运行；有超龄标记测试。

- [ ] **P0-4-3 明确步骤追加的幂等/并发策略**
  - 涉及：`services/storage.py`。
  - 现状：`append_steps()` 用 `count + 1` 计算唯一索引；当前一次运行只调用一次尚未触发，但将来 SSE/重试/并发追加会撞唯一约束。
  - 目标：在同一事务中使用锁定的最大索引、显式序列或幂等 step ID；重复追加不会产生重复记录。
  - 完成标准：连续追加、并发追加和数据库异常测试通过。

## 五、P1：稳定性、可观测性与契约质量

### P1-1 轨迹、日志和上下文

- [ ] **P1-1-1 引入结构化日志**
  - 当前 `app/` 没有正式 `logging` 调用；无法按 run_id 还原模型轮次、工具、错误和耗时。
  - 目标：新增标准库日志配置，在创建/结束 run、每个 Graph 节点和工具调用输出 `run_id/step_index/node/tool_name/error_code/duration_ms`；绝不记录 Token、Key、密码和完整日志。

- [ ] **P1-1-2 填充步骤参数摘要、结果摘要和耗时**
  - 当前 `AgentStep` 虽有 `arguments_summary/result_summary/duration_ms` 字段，但节点没有产生，数据库里长期为空。
  - 目标：只保存 query 长度、KB ID、top_k、来源数量、错误码和耗时；原始 `log_text` 不进入摘要。
  - 完成标准：每个工具步骤都有脱敏摘要和耗时，且能用于定位慢调用。

- [ ] **P1-1-3 限制模型上下文并做不可信内容定界**
  - 当前用户日志、RAG 片段和 observations 直接拼进 HumanMessage；只有自然语言提示，没有 XML/文本定界和 token/字符预算。
  - 目标：用显式“以下均为不可信数据”定界用户输入和工具结果；注入模型前按 chunk/观察边界截断，保留来源 metadata；原始内容不当作指令。
  - 完成标准：包含“忽略系统提示”等恶意文本的样例不会改变工具白名单、路由或证据来源。

- [ ] **P1-1-4 增强 `analyze_log` 信号解释性**
  - 当前只返回信号类型和统一的“命中日志关键词”，没有命中片段、行号和明确边界。
  - 目标：返回 `type/matched_text/line_number`；使用显式数字边界，覆盖常见 5xx 并避免误报。
  - 完成标准：`15020` 不命中，`502-Bad Gateway` 命中，`MySQL OperationalError` 带行号和片段。

### P1-2 报告、模型和异常契约

- [ ] **P1-2-1 报告 JSON 增加一次容错修复**
  - 当前 Markdown 围栏、前后解释文字或轻微格式错误会直接导致整次降级。
  - 目标：剥离代码围栏；首次校验失败后最多进行一次受限修复请求；两次失败仍走降级并记录重试步骤，不无限重试。

- [ ] **P1-2-2 模型配置集中化**
  - 当前 temperature=0.1 等配置写死，每次请求创建模型实例，报告模型与决策模型默认共用。
  - 目标：将模型名、temperature、max_tokens、timeout、max_retries、报告模型名提到 Settings 和 `.env.example`，必要时复用安全的客户端实例。

- [ ] **P1-2-3 使用带时区 UTC 时间**
  - 当前模型使用 `datetime.utcnow()`，Python 3.13 产生弃用警告。
  - 目标：使用 `datetime.now(UTC)` 与带时区列；新增 Alembic 迁移，保证耗时和前端 ISO 8601 展示正确。

- [ ] **P1-2-4 统一异常处理器**
  - 当前 `execute_incident` 之外的数据库或 schema 异常仍可能由 FastAPI 返回通用 500；上游错误类别也被过度折叠。
  - 目标：统一返回安全的错误码和摘要，服务端日志保留 run_id；不向客户端返回路径、堆栈和 `str(exc)`；鉴权代理区分 422、429、5xx、超时。

### P1-3 历史接口和数据访问

- [ ] **P1-3-1 修复历史列表 N+1 并瘦身响应**
  - 当前访问 N 条 run 的 steps 会产生 N+1 查询，列表却返回完整 observations/steps，而前端只使用少量字段。
  - 目标：`selectinload` 或等价批量查询；列表返回 `RunSummary`（ID、标题、状态、KB、时间、计数、错误摘要），详情接口返回完整轨迹。

- [ ] **P1-3-2 补齐时间、耗时和状态字段**
  - `AgentRun` 有时间字段，但 `RunResponse` 和前端历史没有时间、耗时和标题。
  - 目标：列表/详情返回 `started_at/completed_at/duration_ms`，前端展示相对时间和状态细分。

- [ ] **P1-3-3 历史分页、过滤和保留策略**
  - 当前最多加载 100 条完整记录，没有 cursor、时间/状态过滤和清理策略。
  - 目标：支持分页、状态和时间范围过滤；明确历史保留期限、删除和审计策略。

- [ ] **P1-3-4 owner 隔离和失败分支回归测试**
  - 当前没有自动化验证“猜中别人的 run_id 也只能 404”、数据库写入失败、过期 Token 和失败状态持久化。
  - 完成标准：不同用户、未知 ID、过期 Token、数据库异常均有测试。

### P1-4 测试与工程化

- [ ] **P1-4-2 修复全仓 Ruff 门禁**

### P1-5 前端质量

- [ ] **P1-5-1 拆分多语句单行代码**
  - 当前多个 Vue 文件把声明和模板压成单行，影响评审、调试和后续修改。
  - 目标：按 Vue/TypeScript 常规格式展开声明、模板和组合式逻辑，不改变业务行为。

- [ ] **P1-5-2 前后端类型统一**
  - `web/src/types/api.ts` 与 Pydantic/OpenAPI 已出现字段漂移，例如步骤摘要、耗时和 `ok` 字段不一致。
  - 目标：由 OpenAPI 生成 TS 类型，或在 CI 比对手写类型；删除双方都不用的字段。

- [ ] **P1-5-3 前端测试和可访问性**
  - 当前没有 Vitest/组件测试；焦点环被去掉，历史抽屉没有 dialog/ESC/焦点管理，加载状态没有 aria-live，也没有减少动态效果支持。
  - 目标：增加关键 store/组件测试、`:focus-visible`、键盘导航、`role=dialog`、ESC 关闭、`aria-live` 和 `prefers-reduced-motion`。

- [ ] **P1-5-4 统一 401 处理并区分网络故障**
  - 当前只有请求拦截器，没有响应拦截器；工作台用中文错误文案包含“401”判断退出；`auth.restore()` 遇到网络抖动也直接清 Token。
  - 目标：响应拦截器按 HTTP 状态处理 401，保留 redirect；后端不可达只提示，不强制退出。

- [ ] **P1-5-5 历史抽屉使用详情接口**
  - 当前只调用列表接口，显示截短 run_id、状态和 observation 数量，不展示标题、时间、耗时，也没有加载更多。
  - 目标：列表 summary + 点击详情加载完整轨迹；支持分页、重跑和清晰的失败状态。

- [ ] **P1-5-6 前置校验和字段级错误提示**
  - 当前知识库 ID 为空可能变成 `NaN`；422 数组错误被压成一句通用文案；不同失败状态都可能显示 DEGRADED。
  - 目标：提交前校验必填/范围；按 `loc` 映射字段错误；细分 `interrupted`、`timeout`、`max_iterations`、`report_validation_failed` 等状态。

## 十一、当前结论

Incident Agent 的 MVP 主链路已经能够运行：

```text
登录
→ 提交故障标题、日志和知识库 ID
→ AgentState 初始化
→ 模型选择白名单工具
→ 日志分析 / DevAtlas 检索 / 模拟服务状态
→ observe 整理观察
→ Graph 循环或达到上限
→ Pydantic 结构化报告
→ MySQL 保存运行和步骤历史
```

现在最值得做的不是继续增加框架，而是先完成批次 A：把参数真正贯通、固定知识库范围、前置授权、敏感数据脱敏、零证据状态和证据来源核验补齐。完成这些后，再根据时间和面试价值决定是否进入 P1/P2。
