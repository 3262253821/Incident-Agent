## 3. 项目定位和边界

### Incident Agent

面向研发/运维的故障初步分析 Agent：

```text
故障标题 + 日志 + knowledge_base_id
→ 模型选择工具
→ 日志分析、知识检索、服务状态
→ LangGraph 状态和轨迹
→ 异常/循环控制
→ Pydantic 校验的结构化报告
```

不执行重启、Shell、改配置或其他生产操作。

### DevAtlas

`E:\RagKnowledgeSystem` 是底层研发知识库平台，负责：认证、知识库权限、文档上传/版本/切分、Embedding、Chroma 检索和 RAG 基础能力。

Incident Agent 只复用 DevAtlas 的纯检索接口：

```text
POST /api/v1/knowledge-bases/{knowledge_base_id}/search
```

不能调用 DevAtlas 的：

```text
POST /api/v1/knowledge-bases/{knowledge_base_id}/incidents/stream
```

因为后者已经包含“检索 → LLM → 故障分析 → 保存”，Agent 调用它会形成重复 LLM 和重复故障分析流程。

Incident Agent 后续采用：

```text
后端：Python、FastAPI、LangGraph、Pydantic、SQLAlchemy、Alembic
数据库：独立 MySQL 数据库 incident_agent
前端：Vue 3、TypeScript、Vite、Axios
```

Web MVP 采用 DevAtlas JWT 登录态复用：

```text
Agent Web → Agent API（Bearer JWT）
Agent API → DevAtlas /auth/me 获取当前用户 ID
Agent API → DevAtlas /search 时转发 Bearer JWT
```

Agent 只保存 `owner_user_id`，绝不保存 JWT 原文。

4. MySQL 的 `root` 仅用于本机开发，部署时应改为独立的最小权限数据库用户；
5. 工具层离线测试中的 `MockRagGateway` 不依赖真实 JWT 或 DevAtlas；
6. PowerShell 终端曾出现中文显示乱码，但 Python 数据本身正确，属于终端编码展示问题；
7. 不要因为日志提到 MySQL 就假设 `get_service_status("mysql")` 可用；当前 mock 服务只有 `order-service` 和 `user-service`，未知服务应返回 `UNKNOWN_SERVICE`；
8. 当前严格失败策略：一轮任意工具返回 `ok=false`，后续 Graph 应走降级路径；
9. 报告真实引用必须来自 DevAtlas `document_id/version_id/chunk_index` metadata，不能只相信模型文字。
